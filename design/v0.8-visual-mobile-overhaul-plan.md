# The Lantern Line v0.8 Visual and Mobile Overhaul Plan

Date: September 23, 2026

Status: Authoritative implementation plan, independently audited and revised

## Executive decision

Build v0.8 as a **2.5D production pipeline and runtime**, not as a
desktop-first full-3D rewrite.

The game will gain:

- Script-authored 3D models for the locomotive, six car families, threats,
  Longshadow, landmarks, props, and effects.
- High-quality baked sprite parts, animation sheets, normal maps, material
  masks, and shadow layers generated from those 3D sources.
- Layered Godot animation rigs for train mechanisms, crew, enemies, damage,
  and the boss.
- Selective live 3D for high-value cinematics and landmarks when measured
  Web/mobile performance permits it.
- A dedicated touch interface and input router instead of a compressed desktop
  HUD.
- Automatic presentation tiers and per-feature fallback switches.
- A repeatable asset factory that Copilot can operate, inspect, revise, and
  rebuild without depending on an external artist or unreproducible GUI work.

This choice is driven by the WebGL 2 / Compatibility runtime, compact-screen
readability, deterministic gameplay, and rollback safety. It is **not** driven
by an inability to author 3D. The pipeline deliberately keeps 3D authorship
first-class and includes an empirical live-3D benchmark before fixing the
final amount of runtime 3D.

## Desired player-facing result

The v0.8 game should feel like the same strategy game rebuilt as a polished
animated diorama:

1. The train should have mass, suspension, moving machinery, readable damage,
   powered and unpowered states, crew activity, and silhouette-changing
   upgrades.
2. Threats should be identifiable by motion and shape before labels appear.
3. Impacts, defenses, beam interactions, detachments, and boss responses should
   have immediate anticipation, contact, reaction, and recovery.
4. The environment should feel deep and varied without obscuring aiming.
5. On a landscape phone, the central battlefield should remain readable and
   every primary action should be comfortable with touch alone.
6. Accessibility modes should be authored variants of the new presentation,
   not emergency reductions added at the end.

## Research and audit basis

### Current technical baseline

- Godot 4.7.2 with the Compatibility renderer is mandatory for the Web build.
- The game uses a 1280 x 720 logical base, `canvas_items`, and `expand`.
- The Web export is single-threaded and currently boots correctly at
  1280 x 720 and 844 x 390.
- The current public PCK is 3,816,264 bytes.
- The current generated asset tree is approximately 6.1 MB.
- Current world art is mostly immediate-mode `_draw()` code in:
  - `scripts/world/world_renderer.gd`
  - `scripts/train/train_renderer.gd`
  - `scripts/combat/enemy_director.gd`
  - `scripts/combat/longshadow_encounter.gd`
  - `scripts/effects/effects_layer.gd`
- The simulation and rendering of enemies and Longshadow are presently
  co-located, so visual replacement first requires clean view boundaries.
- No explicit `InputEventScreenTouch` or `InputEventScreenDrag` path exists.
- At 844 x 390, several controls are physically far below a 48-pixel touch
  target after the expanded logical viewport is scaled to the browser window.
- v0.7 recorded the following provisional measurements:

| Probe | FPS | Average frame | Worst recorded frame | Draw calls |
|---|---:|---:|---:|---:|
| Desktop gameplay | 60 | 17.05 ms | 145.21 ms | 287 |
| Dense combat | 60 | 17.05 ms | 141.80 ms | 451 |
| Audio stress | 60 | 17.36 ms | 147.10 ms | 345 |

These values prove the scale of the current UI-heavy scene, but the old probe
did not discard warm-up frames or record percentiles. M0 must remeasure all
three scenarios over three warm runs and publish
`design/audits/v0.8-baseline.md`. Final v0.8 gates reference that new baseline,
not the provisional numbers above. A blanket 120-draw-call budget would not
describe the current scene and is not an honest release gate.

### Official platform findings

- Godot Web uses the Compatibility renderer and WebGL 2. Full 3D is possible,
  but Forward+ and Mobile renderer features are not available on Web.
- Compatibility lacks compute-driven effects and the richer post-processing
  path that would normally carry a high-end real-time 3D presentation.
- Godot supports `AnimatedSprite2D`, `AnimationPlayer`, `AnimationTree`,
  `Skeleton2D`, `CanvasTexture` normal/specular maps, 2D lights, particle
  systems, `SubViewport` composition, and glTF imports.
- `InputEventScreenTouch` identifies individual touches and cancellation.
  `InputEventScreenDrag.screen_relative` is explicitly intended for
  resolution-independent touch aiming.
- Godot 4.7 exposes `VirtualJoystick`, but direct world dragging remains the
  preferred primary aiming model for this game.
- `DisplayServer.get_display_safe_area()` covers native Android and iOS.
  Web safe areas require the custom HTML shell and CSS environment insets.
- Browser fullscreen must originate from an intentional user gesture.
- Apple guidance uses 44-point touch targets; Android guidance uses 48 dp.
  v0.8 uses a stricter common target of at least 48 physical/CSS pixels for
  every primary gameplay control.
- Blender 4.5 LTS is supported through July 2027. M0 verifies the selected
  4.5.x patch against Blender's official archive, records its URL and SHA-256,
  and commits that exact version as the production pin before any asset is
  generated.

### Architecture comparison

| Option | Visual gain | Web/mobile risk | Migration risk | Editability | Decision |
|---|---:|---:|---:|---:|---|
| Improved procedural 2D only | Medium | Low | Low | High | Insufficient as the primary target |
| Baked 3D-to-2D with layered rigs | Very high | Low-medium | Medium | High | Primary runtime |
| Hybrid with selective live 3D | Very high | Medium when gated | Medium | High | Included after benchmarks |
| Full real-time 3D gameplay | High | High | Very high | High | Benchmark only, not the default plan |

Full real-time 3D is not impossible. It is rejected as the default because it
would replace proven screen-space gameplay with a more expensive camera,
lighting, culling, animation, and coordinate-mapping stack while weakening the
mobile floor. The plan nevertheless includes a representative live-3D spike
so the final boundary is set by measurements rather than assumptions.

## Non-negotiable contracts

### Gameplay contract

- Presentation must not alter campaign timing, damage, aiming tests, resource
  flow, random streams, route outcomes, saves, or balance.
- Visual animation reads simulation state. Animation frames never become the
  source of gameplay events.
- The same seed and inputs must produce identical outcomes in every visual
  quality tier.
- Existing save schema remains compatible.

### Accessibility contract

- No critical state is communicated only by color, sound, animation, depth, or
  flash.
- High Contrast receives authored outlines, labels, material variants, and
  occlusion rules for every new asset class.
- Reduced Motion stops nonessential parallax, camera travel, bobbing, swaying,
  and procedural drift while keeping attack timing readable.
- Reduced Flashes replaces bright pulses with local outlines, shape changes,
  and sustained markers.
- Existing text scales and keyboard controls remain supported.
- Touch controls have visible focus/pressed states and equivalent keyboard
  actions.

### Tool-sovereignty contract

- Copilot must be able to create, modify, rebuild, and validate every shipping
  visual asset.
- No production step may require an external artist or a GUI-only operation.
- Complex art must not be rejected merely because it is harder to manipulate
  textually.
- Opaque binary-only assets without a documented scripted edit/export path do
  not ship.
- Every generated asset has provenance, parameters, tool versions, and a
  reproducible build command.
- Every category emits visual review artifacts that can be inspected without
  opening Blender.

### Release and rollback contract

- Existing vector renderers remain available behind feature flags through the
  v0.8 release.
- Every migrated category can independently fall back to its v0.7 renderer.
- Desktop HUD and touch HUD coexist.
- Live 3D can be disabled without changing gameplay or baked-sprite rendering.
- A failed stage is corrected or rolled back before the next stage begins.

## Target runtime architecture

### Presentation profiles

The first implementation uses four explicit profiles:

| Profile | Intended use | Features |
|---|---|---|
| `high` | Desktop and proven fast devices | Full-resolution baked art, normal maps, local 2D lights, full particles, optional live-3D cinematics |
| `medium` | Typical mobile Web | Full baked art, no shadow-casting 2D lights, half particles, no live 3D |
| `low` | Constrained mobile / battery saver | Half-resolution baked art, no normal/specular pass, minimal particles and parallax |
| `vector_fallback` | Emergency rollback and visual A/B testing | Existing v0.7 drawing code |

The vector renderer is not automatically assumed to be the cheapest path.
Sprite batching may outperform many immediate-mode primitives. M0/M3
measurements decide whether `low` uses half-resolution sprites or the vector
renderer by default.

Profile selection rules:

1. Start from a conservative platform default.
2. Measure warm gameplay after asset loading, not the title screen.
3. Use rolling p50/p95 frame time after a warm-up period.
4. Demote only at safe transitions, never during an attack.
5. Never auto-promote more than once in a run.
6. Persist the result but retain a manual override.
7. Accessibility settings override visual profile features where required.

`vector_fallback` is never auto-selected. It is a manual recovery and A/B
profile. If `low` cannot sustain the hard floor, the game surfaces a diagnostic
suggesting `vector_fallback` instead of silently changing art styles.

### Simulation/view separation

The new presentation cannot be grafted safely onto the current combined
simulation-and-drawing classes. Split ownership as follows:

- `EnemyDirector` remains the deterministic enemy simulation owner.
- `EnemyViewPool` owns pooled visual scenes keyed by stable runtime enemy IDs.
- `LongshadowEncounter` remains the boss simulation owner.
- `LongshadowView` owns body, tendrils, phase transitions, telegraphs, and
  accessibility variants.
- `TrainRenderer` becomes a small presentation facade.
- `TrainSpriteView` owns locomotive, car, crew, damage, upgrade, and detachment
  visual nodes.
- `WorldRenderer` remains the vector fallback.
- `WorldSpriteView` owns parallax, landmarks, weather, rails, and route-context
  visuals.
- `EffectsLayer` remains the fallback and screen-overlay coordinator.
- `VfxPool` owns the new particle and flipbook effects.

The views receive immutable visual snapshots or direct read-only state. They
may not mutate `RunState`, consume gameplay RNG, or call gameplay actions.
Simulation remains on the existing fixed physics cadence. A pooled
`PresentationSnapshot` is updated on physics ticks, and views interpolate
between the previous and current snapshots using Godot's physics-interpolation
fraction. Reduced Motion may hold the latest snapshot where interpolation is
nonessential. No per-frame snapshot allocation is allowed.

### Visual event boundary

Separate one-shot events into two channels.

`SimEvent` is emitted only by deterministic simulation owners. Views subscribe
read-only:

- train hit
- car hit / critical / destroyed
- defense fired
- enemy spawned / telegraphed / attacked / hit / killed
- ward formed / cracked / shattered
- route reveal / route commit
- station arrival / departure
- detach released
- boss phase entry / response / attack / defeat
- dawn arrival

`PresentationEvent` is emitted only by views and may be consumed only by other
presentation systems:

- beam acquired / focused visual response
- detach armed / canceled flourish
- camera impulse
- particle burst
- UI emphasis

Continuous state such as position, integrity, power, current lens, and
cooldowns remains snapshot-driven. Events carry IDs and timestamps but never
change gameplay. A startup connection audit fails if a simulation callable is
connected to `PresentationEvent` or a view attempts to emit `SimEvent`.

### Coordinate contract

- Simulation remains in the existing 2D logical coordinate system.
- Baked sprites use pivots and sockets exported in logical-space metadata.
- Any live 3D scene receives positions through one tested
  `ScreenWorldMapper`, not ad hoc projection code.
- The reference mapping uses a 1280 x 720 viewport and an orthographic camera
  whose vertical size is 720 world units. A 640 x 360 cinematic SubViewport
  uses the same logical mapping at half resolution.
- Near/far defaults are 0.1 / 100.0. Z is presentational only and is never read
  by simulation.
- `ScreenWorldMapper` owns world-to-screen, screen-to-world-plane, viewport
  scaling, and camera offset. Its test scene round-trips at least 100 points at
  1280 x 720, 960 x 540, 844 x 390, and 640 x 360.
- Headlight tests and enemy hit geometry remain 2D.
- Accessibility labels and all HUD remain in `CanvasLayer`.

## Autonomous asset-production pipeline

### Pinned tooling

- Godot: existing 4.7.2 executable.
- Blender: portable Blender 4.5 LTS installed by
  `tools/art/install_blender.ps1`. M0 selects one verified 4.5.x patch and
  commits `tools/art/blender_pin.json`; later runs use only that pin.
- Python dependencies: pinned in `tools/art/requirements.txt`.
- Optional image utilities must be installed by the same provisioning script
  and may not be assumed to exist globally.

The install script records:

- download URL
- SHA-256
- installed executable path
- Blender version output
- Python dependency lock hash

The initial image/QA dependency set includes Pillow, NumPy, imageio,
imageio-ffmpeg, and scikit-image. Exact versions are locked after the M0
provisioning test.

### Source-of-truth policy

The pipeline supports two authoring modes so editability does not reduce visual
ambition.

#### Parametric/code-first assets

Best for:

- locomotive and car modules
- wheels, rods, couplings, turrets, vents, pipes, rivets, and armor
- route props and landmarks
- material libraries
- camera and light rigs
- procedural damage and weathering
- particle source meshes

Source:

- Python geometry/material modules
- JSON parameter manifests
- SVG paths for small flat iconography

#### Controlled scene-first assets

Best for:

- Longshadow's organic body
- complex enemy rigs
- hand-shaped silhouette corrections
- weight-painted deformation that becomes unreasonable as pure code

A `.blend` file may be committed as a canonical source when it also has:

- a text manifest describing collections, objects, bones, sockets, materials,
  actions, frame ranges, and export products
- a headless Blender script that can open, modify, validate, render, and export
  it
- deterministic naming and scale conventions
- generated contact sheets and topology/rig reports
- no irreplaceable manual step between source and shipping output

`tools/qa/validate_blend.py` enforces this contract by opening each committed
scene headlessly and comparing its collections, object topology hashes, bone
hierarchy, actions/frame ranges, sockets, and materials with the text manifest.
Drift fails validation until the manifest or scene source is deliberately
updated.

This is intentionally less restrictive than "all geometry must be Python."
The goal is autonomous control, not textual purity.

### Build graph

```text
source manifest + Python/.blend source
  -> validated Blender scene
  -> review turntable and silhouette renders
  -> baked sprite parts / animation frames / normal and mask passes
  -> packed atlas + metadata JSON
  -> generated Godot SpriteFrames, CanvasTextures, and scenes
  -> Godot capture scene
  -> contact sheet, animation strip, accessibility variants, and receipt
```

One command builds a category:

```powershell
python tools\art\build_assets.py --category train --review
```

One command verifies everything:

```powershell
python tools\art\build_assets.py --all --verify --review
```

### Determinism and caching

- Pin Blender and Python package versions.
- Seed all procedural work from stable asset IDs.
- Use content hashes to rebuild only changed subjects.
- Keep camera, color management, render engine, samples, light rig, output
  format, and compositor graph in versioned manifests.
- CI or the local release pass rebuilds every shipping asset twice and checks
  deterministic metadata and atlas hashes where the renderer permits exact
  output.
- Where exact pixels differ across hardware, compare structure, alpha,
  dimensions, palette, perceptual hash, and SSIM within a recorded tolerance.
- CI renders through CPU Cycles with OpenImageDenoise and produces the
  canonical references. Local GPU rendering is allowed for iteration, but it
  uses a wider perceptual tolerance and cannot replace canonical references
  without a CPU verification pass.
- `verify_provenance.py` walks every generated visual/resource file and
  requires metadata linking it to a source manifest, build command, tool pin,
  and expected hash. Untracked binary output fails the stage audit.

### Visual receipts

Every changed asset category produces:

- neutral turntable sheet
- in-game camera sheet
- pure silhouette sheet
- material and palette sheet
- normal/mask pass sheet
- animation strip with frame numbers
- extreme-pose rig sheet
- default / High Contrast / Reduced Motion examples
- assembled 1280 x 720, 960 x 540, and 844 x 390 game captures
- a machine-readable manifest and Markdown receipt

Subjective review is handled autonomously through:

1. objective asset checks
2. direct image inspection by the implementing agent
3. an independent visual-critic pass over the contact sheets and captures
4. correction and regeneration before the stage audit closes

The user may review these receipts, but user sign-off is not required for the
pipeline to make progress.

## Art-direction extension

`design/presentation_bible.md` remains authoritative. v0.8 extends it rather
than replacing Coal-lit Ink & Brass.

### 3D-to-sprite camera language

- Fixed orthographic side view with a slight elevated/three-quarter bias.
- The bias must reveal roof machinery and material depth without changing the
  established screen-space silhouette.
- Prototype angles of 0, 6, and 10 degrees and select through compact-screen
  captures.
- All gameplay-facing sprites use the same camera, scale, light rig, and color
  management.
- Cinematic live 3D may use restrained camera movement, but returns to the
  exact gameplay composition.

### Materials

Shared material families:

- soot-black painted steel
- worn iron
- hot and cold brass
- coal and ash
- dirty glass
- lantern emissive
- waxed cloth
- greenhouse glass and growth
- bone/pale mineral
- Longshadow void with phase masks

Materials use broad readable value groups. Tiny PBR detail that disappears at
844 x 390 is excluded or baked into larger marks.

### Silhouette rules

- Car identity must survive a one-color silhouette test.
- Every upgrade adds or replaces a silhouette-level attachment.
- Every threat has a different center of mass, locomotion line, and attack
  wind-up.
- Longshadow changes negative-space shape between Veil, Tether, and Charge.
- Damage removes or bends major forms before adding small texture noise.

### Atlas strategy

Do not render an entire train as a large flipbook.

- Static bodies are baked once.
- Wheels, rods, turrets, fans, doors, and gauges are separate sprite parts.
- Godot transforms animate mechanical parts where possible.
- Flipbooks are reserved for deformation, cloth, smoke, supernatural forms,
  and effects that do not read as rigid transforms.
- Normal and material masks are limited to assets that visibly benefit.
- High and low atlases share pivots and metadata.

This layered approach gives smoother motion, smaller atlases, easier damage
variants, and better upgrade composition than full-frame train sheets.

## Animation implementation rules

- `AnimationPlayer` owns authored reusable sequences.
- `AnimationTree` is reserved for crew and Longshadow where blending is
  valuable.
- Tweens own runtime destinations such as target-dependent recoil or UI panel
  movement.
- `AnimatedSprite2D` owns compact enemy deformation and VFX flipbooks.
- Mechanical train parts use transforms instead of full-body frame animation.
- Enemy view scenes are pooled. No per-spawn resource construction.
- Visual-only randomness uses a presentation RNG seeded separately from the
  campaign RNG.
- Animation playback uses real presentation time but receives paused/speed
  state explicitly. It never changes `Engine.time_scale`.
- Reduced Motion can replace a spatial animation with opacity, outline,
  material, or single-frame state without losing timing information.

## Mobile-first interaction design

### Input router

Add one `PointerRouter` that normalizes:

- mouse movement and buttons
- `InputEventScreenTouch`
- `InputEventScreenDrag`
- touch cancellation
- focus loss and application pause

Rules:

- Track the primary world-aim touch by touch index.
- A touch that begins over an interactive Control never becomes an aim touch.
- Additional fingers can activate HUD actions while aim remains held.
- Use event `position` for absolute aim and `screen_relative` for optional
  relative/dexterity mode.
- Cancel detach and all held actions on touch cancellation, focus loss, modal
  open, route/station transition, or finger release outside the control.
- Mouse emulation remains a compatibility fallback, not the primary mobile
  path.

### Physical target sizing

`UITheme` gains physical-size helpers:

- convert a desired physical/CSS size to the expanded logical viewport
- return a minimum 48-pixel touch target
- return safe-area and comfort-gutter margins
- expose phone, compact desktop, and standard layout classes

At 844 x 390, target sizes are computed from the actual canvas transform; they
are not hardcoded as 48 logical units.

Target policy:

- primary gameplay controls: at least 48 physical/CSS pixels
- Focus: 64-72 pixels
- hold-to-detach: at least 56 pixels and separated from Focus
- spacing between primary controls: at least 8 pixels
- no exception for settings or pause on touch layouts
- touch target scale: 100%, 115%, or 130%, independent from but initially
  matched to the existing text-scale preference

### In-run touch HUD

The touch HUD is a separate composition, not a compressed desktop rebuild.

Top strip:

- distance / time / speed
- locomotive integrity and boss state
- compact resources
- pause, speed, and guide

Left thumb rail:

- three vertically stacked lens controls
- current lens description on selection, not permanently

Bottom-center:

- four role selectors in one 216-pixel-wide row
- each role selector permanently includes its assigned 0-3 value
- tapping a role opens one temporary four-level flyout above the row
- the flyout closes after selection or an outside tap, so role and level
  controls do not consume horizontal width simultaneously

Right thumb rail:

- large Focus
- Salvo
- one contextual field-action slot
- when detachment becomes relevant, a protected hold control replaces the
  contextual slot rather than adding another simultaneous button

Center:

- unobstructed world aim surface
- transient hints and threat callouts placed above thumb zones

The exact arrangement must preserve at least 55% of the physical screen height
as unobstructed central world/readability space at 844 x 390. M1 must produce a
labeled hit-region wireframe before implementation and prove the rails, center
row, flyout, safe areas, and 8-pixel gaps fit without overlap.

### Routes, station, guide, and settings

- Route bands become large selectable slabs, but selection and commitment stay
  separate to prevent accidental dangerous-route choices.
- The selected route receives a large persistent outline and summary.
- Commit and reroll controls remain at least 48 pixels high.
- Station becomes a paged or tabbed touch layout rather than a long scaled
  desktop list.
- Car and crew targets use large cards with one primary action per card.
- The guide becomes swipe/page friendly while retaining keyboard navigation.
- Settings use large rows, clear current values, and no hover-only information.

### Safe areas and browser shell

Create a source-controlled custom Web shell rather than editing exported
`docs/index.html` by hand.

The shell provides:

- `viewport-fit=cover`
- CSS `safe-area-inset-*` capture
- landscape/portrait handling
- click-to-start fullscreen request
- AudioContext unlock handoff
- wake-lock request with graceful fallback
- installable PWA metadata and icons
- cache/version display for support

`WebPlatformBridge` reads safe insets through `JavaScriptBridge` and provides
zero insets on desktop. It does not call the desktop
`DisplayServer.get_display_safe_area()` fallback. Native Android/iOS use
`DisplayServer.get_display_safe_area()`. Web creates a CSS probe element,
reads `env(safe-area-inset-*)` through `getComputedStyle`, and forwards four
pixel values through `JavaScriptBridge`.

Use a 24-pixel comfort gutter in addition to detected unsafe insets for
interactive controls.

### Orientation and pause behavior

- Target sensor landscape on native mobile.
- Request landscape-primary in the PWA manifest.
- Show a rotate-device overlay in portrait browser sessions.
- Autosave and pause on application suspension.
- Do not assume every iOS PWA version honors manifest orientation; the overlay
  remains the fallback.

- one shadowed-light configuration
- default and reduced-effects configurations
- 1280 x 720 and 844 x 390 captures

The benchmark compares:

1. full runtime 3D
2. baked layered sprites
3. baked sprites plus a small live-3D background/cinematic layer

Live 3D earns gameplay use only if it:

- completes one warm run and three 30-second measured runs
- sustains p95 <= 24 ms on desktop Web and p95 <= 33 ms on the available
  accelerated Android-class test path
- keeps compact silhouettes at least as readable as baked sprites
- does not require a separate gameplay coordinate system
- does not exceed the memory and package gates
- preserves High Contrast and Reduced Motion without a parallel art rewrite

Expected use even if full gameplay 3D fails:

- Longshadow reveal
- station arrival/departure
- Dawn Beacon victory
- selected route landmarks
- title-screen train diorama

This checkpoint prevents both premature full-3D commitment and an artificially
small 3D scope. Its result is committed as
`design/decisions/v0.8-live-3d-boundary.md`; that decision record is the sole
authority for M6 live-3D scope.

## Performance and package budgets

### Frame-time gates

Desktop Web:

- sustained 60 FPS after warm-up
- p95 frame time <= 20 ms in normal gameplay
- p95 frame time <= 24 ms in dense combat
- no repeated >50 ms stalls after asset warm-up

Mobile Web, selected profile:

- target >=45 FPS
- hard release floor >=30 FPS
- p95 frame time <= 28 ms at the target tier
- no input starvation during dense combat

Performance reports must discard startup/import frames and record p50, p95,
p99, and maximum frame time instead of relying only on a lifetime worst frame.

### Draw-call gates

The v0.7 values 287 / 451 / 345 are provisional scale references only. M0
publishes three-run, post-warm-up values in
`design/audits/v0.8-baseline.md`. All numeric draw-call gates are then set to:

- normal and dense gameplay: no more than +10% over the matching warm baseline
  during migration
- final optimization goal: at least 15% below the matching warm baseline
  through atlas/material reuse and view pooling

If M0 cannot obtain stable three-run values within a 5% range, the gate uses a
range and p95 instead of one absolute count.

### Visual resource gates

- no more than 2 active presentation lights
- no more than 12 active particle emitters
- no more than 800 live particles on High
- no more than 300 live particles on Medium
- no more than 120 live particles on Low
- atlas page maximum: 2048 x 2048
- High peak loaded texture target: <=128 MiB
- Medium target: <=80 MiB
- Low target: <=48 MiB
- normal/material passes are unloaded when the profile does not use them

### Package gates

Track `index.pck`, not an ambiguous total Web bundle that includes the Godot
engine/WASM payload.

- target `index.pck`: <=22 MiB
- hard `index.pck` ceiling: <=26 MiB
- added v0.8 visual payload target: <=16 MiB compressed
- every stage records PCK delta by asset category

Cumulative stage ceilings:

- M3: <=7 MiB
- M4: <=13 MiB
- M5: <=17 MiB
- M6: <=20 MiB
- M7/M8 release candidate: <=22 MiB target

Enable and verify the ETC2/ASTC import path for mobile/Web textures, then force
a clean reimport. Do not treat export-preset booleans as proof; the validation
step must inspect imported resource formats and actual package output.

## Acceptance criteria

The v0.8 plan is complete only when:

- the visual pipeline is reproducible from source
- every new asset is autonomously editable and reviewable
- no required production step depends on external manual art
- the train, cars, threats, boss, world, effects, and UI share one coherent
  visual language
- animation materially improves anticipation, impact, state readability, and
  mechanical weight
- live 3D is used wherever the benchmark proves it adds value safely
- touch-only play can complete the full game comfortably
- primary touch targets meet the physical-size policy
- performance tiers preserve at least the mobile hard floor
- accessibility invariants pass in the new presentation
- deterministic simulation and saves remain unchanged
- every implementation stage has a written audit and corrected findings
- three final playtest/correction rounds complete before release
