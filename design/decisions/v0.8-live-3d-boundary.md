# v0.8 Live-3D Boundary

Date: 2026-09-23

Status: Accepted for M0

## Decision

The Lantern Line will ship v0.8 gameplay with layered baked sprites as the
default renderer. Selective live 3D is approved only for bounded landmarks,
short transitions, and Longshadow presentation on the High profile. Full
runtime-3D train, threat, and combat rendering remains a benchmark tool and is
not approved for production gameplay.

The approved hybrid shape is:

- baked sprite train, cars, crew, regular threats, attacks, and HUD
- a half-resolution live-3D viewport for approved environment or boss content
- no simulation authority inside the live-3D view
- a baked replacement for every live-3D scene
- automatic removal on Medium, Low, vector fallback, touch-auto profiles, and
  unsupported platforms

## Evidence

The native comparison used Godot 4.7.2's Compatibility renderer on an AMD
Radeon 860M, a five-car consist, the full HUD, shared effects, 12 threats for
real pressure, 16 threats for headroom, and a separate boss scene. Pressure
results are medians of three uncapped 30-second measurements after a two-second
warm-up.

| Architecture | Native frame p95 | Draw p95 | Video MiB | Relative draw cost |
|---|---:|---:|---:|---:|
| Baked-sprite proxy | 0.74 ms | 208 | 23.0 | 1.00x |
| Hybrid | 0.91 ms | 292 | 30.8 | 1.40x |
| Full runtime 3D | 1.39 ms | 603 | 34.5 | 2.90x |

At 16-threat headroom, the sprite, hybrid, and runtime-3D paths measured 222,
306, and 643 draw calls respectively. In the boss checkpoint, the hybrid path
measured 1.39 ms frame p95 and 281 draw calls, while full runtime 3D measured
1.39 ms and 509 draw calls.

The WebGL 2 gate ran in Edge 153 through ANGLE/D3D11 on the same Radeon device.
All modes held 60 FPS at 1280 x 720 and 844 x 390 with no page or console
errors. The mobile-width draw counts were 170 for sprites, 254 for hybrid, and
565 for full runtime 3D. This proves WebGL 2 compatibility, not physical-phone
performance.

## Profile policy

| Profile | Baked gameplay | Live 3D | Required fallback |
|---|---|---|---|
| High | Yes | Approved scenes only | Baked |
| Medium | Yes | No | Baked |
| Low | Yes, reduced resolution | No | Baked low atlas |
| Vector fallback | No | No | Existing vector renderer |

`auto` resolves touch-capable platforms conservatively, so live 3D remains off
on phones and tablets unless a later physical-device decision explicitly
changes that rule.

## Admission gate for a live-3D scene

A scene may enter the High profile only when all of the following are true:

1. It is presentation-only and cannot alter simulation outcomes.
2. Its baked replacement has feature and information parity.
3. The integrated scene remains at or below 350 draw calls p95 on desktop Web
   and 300 at the 844 x 390 Web gate.
4. It holds 60 FPS with frame p99 at or below 18.0 ms in the Web gate.
5. It adds no more than 8 MiB video memory over the matching baked scene.
6. Reduced Motion, Reduced Flashes, High Contrast, and text-scale checks pass.
7. First-use shader and resource work is completed during a controlled warm-up.

The final M6 gate additionally requires hardware-accelerated Android-class
evidence before any live-3D scene can be enabled by default on mobile. Physical
or hosted iOS Safari remains a release compatibility check.

## Rejected alternative

Full runtime-3D gameplay is rejected for v0.8 because it nearly triples draw
calls at representative pressure, increases uncapped native frame p95 by about
88%, more than triples draw calls at mobile width, adds about 11.5 MiB of video
memory over the sprite proxy, and provides no mobile-hardware evidence strong
enough to justify the risk. The result is not a claim that runtime 3D is
impossible; it is a scope and reliability decision for this release.
